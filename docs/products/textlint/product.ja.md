# textlint

[English](product.md)

## 概要

textlint は自然言語のためのプラガブルな Lint ツールです。
ESLint に似ていますが、プログラムのコードではなく文章をチェックします。
textlint は Markdown などの文書のマークアップをパースします。マークアップには仕様があるからです。
マークアップの中にある自然言語はパースせず、言語の扱いはルールに任せます。
これにより textlint は、文字列検索（grep）より賢く、しかし人間のように言語を理解しようとはしないツールになっています。

textlint 自体はルールを 1 つも持ちません。
利用者はルール、プリセット、フィルタールールをインストールし、textlint はそれらを Markdown、プレーンテキスト、プラグインが対応するその他の形式で書かれた文書に対して実行します。

## 背景と課題

### 背景

文章の規約は、プロジェクト、言語、文書の種類、読み手によって異なります。
小説、技術書、翻訳では必要なルールが違い、同じ書き手でもブログと書籍では書き方が変わります。
自然言語は時間とともにも変化します。新しい単語は毎日増え、かつては誤りとされた用法が受け入れられるようになり、単語の意味が移り変わることもあります。
そのため、唯一の公式ルールセットは作れず、すべての自然言語の文法を包含する AST も作れません。
そこで textlint は共通の仕組みを提供し、チェックそのものは別パッケージとして配布します。

### 解決する課題

書き手は、文章の構造と用語を機械的にチェックし、CI で動かしたいと考えています。
ここでいう構造とは、パラグラフ、見出し、リスト、文の長さなどです。
1 行ずつ目で確かめるレビューは遅く、人によって結果がばらつきます。
一方、スペースやマークアップの書き方のような、Markdown のリンターが扱うチェックは別の関心事です。
textlint でも動かせますが、そのために作られてはいません。

文書をただの文字列としてチェックすると、マークアップに対して誤検知が起きます。
コードスパン、URL、引用は、文と同じようにチェックすべきではありません。
「文字数」でさえ、Markdown とプレーンテキストでは数え方が異なります。

ルール作者は、チェックを一度書けば、どの文書形式でも動かしたいと考えています。
形式ごとにパースし直す必要があると、同じルールを形式の数だけ書くことになります。

## 対象ユーザー

### 書き手

- **特徴：** Markdown やプレーンテキストで、ドキュメント、書籍、翻訳、小説、Web サイトを書く人。日本語や英語が多い。チームがプロダクト内の表記をそろえるために使うこともある。
- **課題：** 文章規約を人手でレビューすると、遅く、ばらつきが出る。
- **利用場面：** コマンドライン、CI、エディタ連携から textlint を実行する。

### ルール作者とプラグイン作者

- **特徴：** textlint のルール、プリセット、フィルタールール、プラグインを npm パッケージとして公開する開発者。
- **課題：** 文書形式が何であっても、ルールは元の文書の正しい位置を報告しなければならない。
- **利用場面：** ルールの中で TxtAST をたどる。または、プラグインの中で新しい文書形式を TxtAST に変換する。

### 組み込む開発者

- **特徴：** textlint をエディタ、ブラウザ、ボットなどのツールに組み込む開発者。
- **課題：** テキストがある場所で textlint を動かす必要があり、テキストをサーバーに送れないこともある。
- **利用場面：** ブラウザも含めて、textlint のパッケージをモジュールとして使う。

## 提供する価値

### どの形式にも使える 1 つのルール

- **受け取る人：** ルール作者と書き手
- **提供するもの：** プラグインが各文書形式を共通の TxtAST に変換するので、1 つのルールが Markdown、プレーンテキスト、その他の形式で動く。
- **理由：** ルールが依存するのは TxtAST だけで、特定のパーサーには依存しない。

### 書き手の手元で完結するチェック

- **受け取る人：** 書き手と組み込む開発者
- **提供するもの：** textlint と多くのルールはローカルで動き、textlint はブラウザでも動くので、テキストを外部サービスに送る必要がない。
- **理由：** 文書は公開されるまで非公開であることが多い。

## 主要な概念

- **ルール：** TxtAST のノードを受け取り、エラーを報告するチェック。修正を提案することもある。
- **フィルタールール：** 報告されたエラーのうち無視するものを決めるルール。たとえば `<!-- textlint-disable -->` コメントの中のエラーを無視する。
- **プリセット：** 技術文書向けなど、目的ごとにルールをまとめたパッケージ。
- **プラグイン：** 文書形式を TxtAST に変換するパッケージ。Markdown とプレーンテキストのプラグインは組み込まれている。
- **TxtAST：** textlint がルールに渡すノードの木。マークアップの構造を表し、文章はテキストノード（`Str`）に残る。すべてのノードは `type`、`raw`、`range`、`loc` を持つ。すべての形式で共通の汎用ノードは PascalCase の名前（`Str`、`Paragraph`）を持つ。1 つの形式が追加する拡張ノードは小文字で始まる名前（`yaml`、`footnoteReference`）を持つ。そのため、ルールが形式をまたいでそのノードの種類に頼れるかどうかは、大文字か小文字かでわかる。TxtAST は緩く定義する。[Requirements](features/txtast/requirements.ja.md) は、ルールが形式をまたいで頼る部分だけを決める。
- **メッセージ：** ルールが報告するエラー。位置をソース中の範囲として持つ。
- **フォーマッター：** `stylish` や `json` のように、メッセージを出力するパッケージ。

## 開発方針

- **すべてをプラガブルにする。** コアはどのマークアップ言語にも自然言語にも依存しない。新しいマークアップ言語にはプラグイン、新しいチェックにはルール、新しい自然言語はルールの中で扱い、新しい出力にはフォーマッターを使う。textlint 自身が決めるのは AST とメッセージの形式だけである。
- **ルールを組み込まない。** ルールはオプトインにする。デフォルトで誤検知を多く出すツールは無視されるようになり、CI では利用者に 1 件ずつ却下してもらうこともできないからである。ルールはコアの外に置き、言語に依存しないルールは `textlint-rule`、日本語のルールは `textlint-ja` の Organization で管理する。
- **パーサーはコアの近くに置く。** プラグインはマークアップをどう解釈するかを決めるので、組み込みのパーサーとプラグインのコミュニティは `textlint` Organization で管理する。
- **必要なのはパースの部分だけ。** textlint が必要とするのは文書パーサーのうちパースの部分である。汎用の処理フレームワークを持ち込むパーサーは必要ない。
- **TxtAST は言語に依存しない。** 1 つの形式にしかない構文を TxtAST の一部にする必要はない。
- **ブラウザで動く。** カーネルが読み込むパッケージは、パーサーも含めて Node.js 専用の API を避け、サーバーなしで textlint を動かせるようにする。
- **実際の文書で確かめる。** 手書きのテストケースだけでなく、textlint を使って書かれた書籍やドキュメントのような実際の文書で挙動を確かめる。
- **使うものを作る。** textlint を使って本を書くなど、実際のユースケースがあることで開発が進む。
