# Markdown のパースの設計

[English](design.md)

## この文書について

この設計は、`@textlint/markdown-to-ast` が [textlint の Product](../../product.ja.md) の [Markdown のパースの Requirements](requirements.ja.md) をどう満たすかを説明します。

### 読者

`@textlint/markdown-to-ast` または `@textlint/textlint-plugin-markdown` を変更する人とエージェント。

### 前提知識

- [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) と [GFM](https://github.github.com/gfm/) の仕様
- `@textlint/ast-node-types` の `TxtNode` インターフェース

### この文書の範囲外

ルールが TxtAST をたどる方法と、プレーンテキストのパーサー。

## 実装の方針

パッケージは、TxtAST を直接生成する独自の CommonMark + GFM パーサーを持ちます。
textlint が必要とするのは Markdown 処理系のうちパースの部分だけなので、unified/remark のような汎用フレームワークには依存せず、mdast のような中間の AST も作りません。

パースは 1 つのソース文字列に対して 3 つのフェーズで進みます。

1. **ブロックフェーズ：** CommonMark のコンテナーのアルゴリズムで、テキストを 1 行ずつ走査します。
   引用、リスト、リスト項目を開いたり閉じたりし、段落、見出し、コードブロック、HTML ブロック、テーブル、フロントマターなどの末端のブロックを作ります。
   末端のブロックはテキストをコピーせず、行をセグメント（開始と終了のオフセット）として持ちます。
2. **インラインフェーズ：** 段落、見出し、テーブルのセルのセグメントをインラインのノードにパースします。
   強調、重要、取り消し線は CommonMark の区切り記号スタックを、リンクと画像は角括弧スタックを使います。
   ブロックフェーズで集めたリンク参照定義で `LinkReference` と `ImageReference` を解決します。
3. **出力フェーズ：** ノードプールを 1 回たどり、`TxtNode` のオブジェクトを作ります。
   `raw` と通常の `value` の文字列はこの時点でソースから切り出し、`loc` は行の開始オフセットの表から計算します。

3 つのフェーズは 1 つのノードプールを共有します。
プールは「配列の構造体（struct of arrays）」です。ノードの各フィールド（`kind`、`start`、`end`、`parent`、`firstChild`、`nextSibling`、ペイロードのスロット）がそれぞれ型付き配列になっていて、ノード同士はインデックスで参照し合います。
出力フェーズまではノードのオブジェクトを作らず、プールは次の `parse()` の呼び出しで再利用します。
バックスラッシュエスケープや文字参照のようにデコードが必要な文字列は、別の表に保存します。

BOM はパースの前に取り除き、位置は BOM を除いて数えます。

各フェーズは、作業中の状態を呼び出しスタックではなく平らな配列に持ちます。
ブロックフェーズは、開いているコンテナーのスタックを持ちます。
インラインフェーズは、区切り記号スタック、角括弧スタック、開いているインライン注のスタックを持ちます。
複数行にまたがるブロックは、セグメントをつないだバッファーを通してパースし、インラインのノードを仕上げるときにバッファー上の位置をソースのオフセットへ戻します。
区切り記号スタックの中では、取り消し線を強調より先に解決します。

### remark ベースのパーサーから引き継ぐ挙動

以前の実装は、remark に `remark-gfm`、`remark-frontmatter`、`remark-footnotes` を組み合わせていました。
公開されているルールがその出力に依存しているので、CommonMark や GFM の仕様と違う場合でも、次の挙動を再現します。

- Pandoc 形式のインライン注（`^[note]`）は `footnote` になります。`]` は、リンクを閉じない場合に、直近の開いているインライン注を閉じます。
- 脚注のラベルは空白を含められます。
- `[^label]:` の後では空白文字を 1 つだけ読み飛ばすので、`[^1]:     text` は脚注定義の中のインデントコードブロックになります。
- `[^` はリンクにもリンク参照定義にもなりません。

### 意図して変えた挙動

remark ベースのパーサーで位置が食い違っていた箇所は再現しません。

- 閉じていないフェンスコードブロックや HTML ブロックで終わる `ListItem` は、次の項目と重ならず、その手前で終わります。
- タスクリストのチェックボックスの後ろのテキストの `loc` は、常に `range` と同じ範囲を指します。
- 文書の先頭でフロントマターのフェンスが開けなかった場合でも、文書の残りでのリスト項目の認識は変わりません。

## アーキテクチャとシーケンス図

図は必要ありません。`parse()` は 3 つのフェーズを順に呼び出し、どのフェーズも文字参照の表以外のモジュールを呼び出しません。

## データモデルと ER 図

出力は `@textlint/ast-node-types` で定義された `TxtNode` の木で、ノードの種類は [Requirements](requirements.ja.md#ノードの種類) に挙げたものです。

内部のノードプールは公開しません。プールはノードごとに、種類、開始と終了のオフセット、親・最初の子・最後の子・前の兄弟・次の兄弟のインデックス、種類によって意味が変わるペイロードのスロット（見出しの深さ、リストの開始番号、別の表へのインデックスなど）を持ちます。

## API とインターフェース

関数は `parse(text: string): TxtDocumentNode` だけで、`Syntax` は `ASTNodeTypes` を再エクスポートします。

ノードは `TxtNode` とそのノードの種類のプロパティだけを持ちます。
ルールは `range` と `loc` を使うので、unist との互換性のための隠しプロパティ `position` は持ちません。

## 外部サービスとの連携

なし。パッケージには外部の実行時依存がありません。
パーサーは ECMAScript の組み込み機能（型付き配列、文字列、Unicode プロパティエスケープを使う正規表現）だけを使い、Node.js のモジュールを使わないので、[Requirements](requirements.ja.md#サーバーなしでパースする) のとおり、そのままブラウザで動きます。
名前付き文字参照の表は、パッケージ内のスクリプトで [WHATWG の entities.json](https://html.spec.whatwg.org/entities.json) から生成し、ソースとしてコミットします。そのため実行時にデータを取得しません。

## データの扱い

なし。ソースのテキストは `parse` が返った後には保持しません。ただし、再利用するプールは確保した容量を保ちます。

## 認証と認可の注意

なし。パースにはアクセス制御がありません。

## セキュリティの考慮事項

[Requirements のセキュリティの考慮事項](requirements.ja.md#セキュリティの考慮事項)は、細工された文書でもパースが止まらず、コールスタックがあふれないことを求めています。

どのフェーズも入力を読み戻さないので、パースの時間は入力の大きさにほぼ比例します。
インラインのパースは CommonMark の区切り記号スタックと角括弧スタックのアルゴリズムを使い、閉じていない括弧や区切り記号を何度も読み直さずに扱います。ブロックフェーズは、各行を開いているコンテナーごとに 1 回ずつ見ます。

入れ子の深さは文書が決めるので、パーサーは 100 段という決まった上限（`MAX_NESTING`）を、ブロックとインラインに別々に設けます。

ブロックでは、`Document` の下で開いているコンテナーのスタックが上限を超えません。
引用と脚注の定義はそれぞれ 1 段、リスト項目は `List` と `ListItem` の 2 段を使うので、リストは 50 段まで入れ子になります。
コンテナーが上限を超えることになるときは開かず、その記号は段落やその続きのような、今のコンテナーの通常のテキストとして扱います。

インラインでは、上限は区切り記号の数ではなく、インラインの部分木の高さに適用します。
`Emphasis`、`Strong`、`Delete`、`Link`、`LinkReference`、`footnote` はそれぞれ 1 段を加えます。
ノードが上限より高くなる区切り記号や角括弧の組は対応づけず、その記号はテキストのまま残します。そのため、内側の 100 段が残り、外側の記号がテキストになります。
`Image` は子を残さないので数えません。
上限に達した後は、区切り記号の探索でそれより前の区切り記号を読み直さないので、深い入力でも時間は線形のままです。
開く側が見つからなかった閉じる側の区切り記号も、どこまでさかのぼって探したかを記録するので、後ろの閉じる側が同じ範囲をもう一度探すことはありません。

ブロックとインラインを別々に制限するので、いちばん深い AST はおよそ `Document`、100 段のコンテナー、`Paragraph` または `TableCell`、100 段のインライン、`Str` です。
入れ子の深さに応じて再帰するフェーズはありません。
深さが AST に従う木の走査は、インラインの仕上げ、画像の代替テキストの収集、出力フェーズの 3 つで、再帰ではなく親へのリンクか明示的なスタックを使います。
上限だけでも再帰は安全ですが、ループにしておくことで、後から上限を上げてもパーサーは安全なままです。

ほかの理由で `parse` が例外を投げても、次の `parse()` の呼び出しがプールをリセットするので、失敗が後の文書に影響しません。

## デプロイの注意

ノードの種類やプロパティを変えると、それに頼るルールが壊れます。そのため、そのような変更はメジャーバージョンでだけリリースし、変更点をリリースノートに挙げます。

## 検討した代替案

### remark を使い続ける

remark のエコシステムに追従でき、`remark-cjk-friendly` のような remark のプラグインを使えます。
remark は変換や書き出しも扱う汎用の Markdown 処理系ですが、textlint が使うのはパーサーだけで、その結果を独自の AST に変換しています。
3 つの理由で採用しませんでした。
書き出しのように textlint が使わないパッケージを持ち込みます。
mdast から TxtAST への変換には、mdast が位置を持たせないノードのための位置の回避策が必要です。
長いテーブルや閉じていない大量の括弧のように、大きさから想像するよりはるかに時間がかかる入力があり、セキュリティの考慮事項と食い違います。

### micromark と mdast-util-from-markdown を直接使う

unified/remark の層をなくし、micromark をトークナイザーとして残す方法です（[#2187](https://github.com/textlint/textlint/pull/2187)）。
外部パッケージはおよそ半分に減り、Pandoc 形式のインライン注（`remark-footnotes` が必要）を除いて同じ AST になります。
パースの時間の大部分を占める micromark のトークナイザーと、mdast からの変換が残るため、採用しませんでした。

### 自前のパーサーを保守する（採用）

textlint が独自のパーサーを保守し、CommonMark と GFM の今後の変更にも自分で追従する必要があります。
CommonMark と GFM は公式の例を持つ文書化された仕様なので振る舞いをテストでき、Requirements に挙げた拡張以外に textlint 独自の構文は足さないため、この負担を受け入れます。

## 未解決事項

- **CJK に配慮した強調：** CJK の句読点の隣にある強調を認識するオプトインのオプションが textlint/textlint#2113 で提案されている。この設計では、[markdown-cjk-friendly の仕様](https://github.com/tats-u/markdown-cjk-friendly)に従ってインラインフェーズに実装し、`parse` にオプションの引数を加える。Requirements で決まるまで、`parse` はオプションを持たない。azu が PR の作者と決める。
