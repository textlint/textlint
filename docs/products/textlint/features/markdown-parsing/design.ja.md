# Markdown のパースの設計

[English](design.md)

## この文書について

この設計は、`@textlint/markdown-to-ast` が [textlint の Product](../../product.ja.md) の [Markdown のパースの Requirements](requirements.ja.md) をどう満たすかを説明します。

### 読者

`@textlint/markdown-to-ast` または `@textlint/textlint-plugin-markdown` を変更する人とエージェント。

### 前提知識

- [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/) と [GFM](https://github.github.com/gfm/) の仕様
- `@textlint/ast-node-types` の `TxtNode` インターフェース

### この文書の範囲外

ルールが TxtAST をたどる方法と、プレーンテキストのパーサー。

## 実装の方針

パッケージは、TxtAST を直接生成する独自の CommonMark + GFM パーサーを持ちます。
textlint が必要とするのは Markdown 処理系のうちパースの部分だけなので、unified/remark のような汎用フレームワークには依存せず、mdast のような中間の AST も作りません。

パースは 1 つのソース文字列に対して 3 つのフェーズで進みます。

1. **ブロックフェーズ：** CommonMark のコンテナーのアルゴリズムで、テキストを 1 行ずつ走査します。
   引用、リスト、リスト項目を開いたり閉じたりし、段落、見出し、コードブロック、HTML ブロック、テーブル、フロントマターなどの末端のブロックを作ります。
   末端のブロックはテキストをコピーせず、行をセグメント（開始と終了のオフセット）として持ちます。
2. **インラインフェーズ：** 段落、見出し、テーブルのセルのセグメントをインラインのノードにパースします。
   強調、重要、取り消し線は CommonMark の区切り記号スタックを、リンクと画像は角括弧スタックを使います。
   ブロックフェーズで集めたリンク参照定義で `LinkReference` と `ImageReference` を解決します。
3. **出力フェーズ：** ノードプールを 1 回たどり、`TxtNode` のオブジェクトを作ります。
   `raw` と通常の `value` の文字列はこの時点でソースから切り出し、`loc` は行の開始オフセットの表から計算します。

3 つのフェーズは 1 つのノードプールを共有します。
プールは「配列の構造体（struct of arrays）」です。ノードの各フィールド（`kind`、`start`、`end`、`parent`、`firstChild`、`nextSibling`、ペイロードのスロット）がそれぞれ型付き配列になっていて、ノード同士はインデックスで参照し合います。
出力フェーズまではノードのオブジェクトを作らず、プールは次の `parse()` の呼び出しで再利用します。
バックスラッシュによるエスケープや文字参照のようにデコードが必要な文字列は、別の表に保存します。

BOM はパースの前に取り除き、位置は BOM を除いて数えます。

### なぜ独自のパーサーなのか

以前の実装は、`remark-parse`（micromark）に `remark-gfm`、`remark-frontmatter`、`remark-footnotes` を組み合わせ、mdast を TxtAST に変換していました。
次の理由で置き換えました。

- textlint に必要なのはパースだけだが、remark 一式は、textlint が使わない書き出し用のパッケージも含めて約 96 個の外部パッケージを持ち込んでいた。
- パースの時間の大半は micromark のトークナイザーと変換のための走査にかかっていて、数十秒かかる入力もあった（[セキュリティの考慮事項](#セキュリティの考慮事項)を参照）。
- 位置のないノードのための回避策が必要で、位置の不具合のうち 2 つは micromark/mdast の層に由来していた。
- CommonMark は公式の例のテスト一式を持つ安定した仕様なので、外部のパーサーなしでも追従し続けられる。

これは textlint の出発点に戻ることでもあります。
textlint の最初のバージョン（2014 年 12 月）は `commonmark` パッケージの AST の上に作られていました。当時ノードの位置を少しでも持っていたパーサーはこれだけで、remark はまだ位置を持っていなかったからです。
ただし、その位置は不完全でした。`commonmark` 0.15 が返すのはブロックの開始行と開始列だけで、インラインのノードには何もありませんでした。
`markdown-to-ast` は AST を Markdown に書き戻して `raw` と終了位置を組み立て直していて、見出しの子ノードの列をずらすといった回避策が入っており、強調の `*` と `__` を区別できませんでした。
2015 年 2 月に `mdast`（remark の前身）0.3 がすべてのノードに開始と終了の位置を持たせたので、`markdown-to-ast` 3.0.0 はそちらに切り替え、CommonMark のコードを削除しました。
独自のパーサーは、その切り替えが必要になった理由を引き継いでいます。すべてのノードが正確な範囲を持ちます。

### 以前の実装との互換性

次のコーパスのすべての入力で、出力される AST は以前の実装と同じです。比較は `range`、`loc`、`raw` を含めた AST 全体で行いました。

| コーパス | 一致 |
| --- | --- |
| `@textlint/markdown-to-ast` のフィクスチャ | 227 / 227 |
| CommonMark 0.31.2 の仕様の例 | 652 / 652 |
| GFM の仕様の例と拡張のテスト | 702 / 702 |
| 実在する `.md` ファイル | 2,852 / 2,852 |
| このリポジトリの Markdown ファイル | 403 / 403 |

Markdown のトークンを組み合わせたランダムな入力では、トークンの集合によって約 0.2〜0.8% のケースで差が出ます。
トップレベルのブロック構造が違う場合、新しいパーサーは多くのケースで GitHub のリファレンス実装である cmark-gfm と一致し、以前の実装が一致することはまれです。
差は次のグループに分かれます。

- **閉じていないフロントマターの区切り：** 以前の実装は、最初の行がフロントマターの区切りに見える場合（たとえば区切り線として使った `---`）、文書全体でリストを認識しなくなっていた。新しいパーサーは CommonMark に従う。
- **改行が続くタスクリスト項目：** 以前の実装は、続く段落に `range` と一致しない `loc` を付けていた。新しいパーサーは両者を一致させる。
- **タブでインデントした段落の行の後のテーブルの見出し：** 新しいパーサーは cmark-gfm と同じくテーブルを始める。以前の実装はその行を段落に残していた。
- **リスト項目や引用の末尾にある閉じていないフェンスのコードや HTML ブロック：** 以前の実装は `ListItem` が次の項目と重なることがあった。新しいパーサーは次の項目の前で終える。引用の中では、閉じていないコードブロックの終わりが末尾の `> ` の分だけ異なることがある。
- **タブを含む入れ子のコンテナー内の末尾の空白：** いくつかの `range` の値が異なる。原因は完全には分かっていない。

`raw === text.slice(range)` の不変条件、`loc` と `range` の一致、子が親の内側にあること、兄弟が重ならないことは、これらすべての入力で両方の実装について成り立ち、`test/invariants.test.ts` で確認しています。

## アーキテクチャとシーケンス図

図は必要ありません。`parse()` は 3 つのフェーズを順に呼ぶだけで、文字参照の表を除き、どのフェーズもほかのモジュールを呼びません。

## データモデルと ER 図

出力は `@textlint/ast-node-types` で定義された `TxtNode` の木で、ノードの種類は [Requirements](requirements.ja.md#ノードの種類) に記載したとおりです。

内部のノードプールは公開しません。ノードごとに、種類、開始と終了のオフセット、親、最初の子、最後の子、前の兄弟、次の兄弟のインデックスと、種類によって意味が変わるペイロードのスロット（たとえば見出しの深さ、リストの開始番号、別の表へのインデックス）を持ちます。

## API とインターフェース

関数は `parse(text: string): TxtDocumentNode` だけで、`Syntax` は `ASTNodeTypes` を再エクスポートします。
どちらも以前の実装と同じです。

以前の実装が unist との互換性のために持たせていた、列挙されない隠しプロパティ `position` は、ノードから削除しました。
`ASTNodeTypes` にないノードの種類は、Product の命名の決まりに従って小文字に変えました。`Yaml`、`Toml`、`Json`、`FootnoteReference` は、`yaml`、`toml`、`json`、`footnoteReference` になります。`Yaml` をチェックしないノードの一覧に入れているルールは、エラーにならずにフロントマターを本文としてチェックするようになるため、リリースノートで明記します。
ルールは `range` と `loc` を使います。`textlint`、`textlint-ja`、`textlint-rule` の Organization では `position` の利用は見つかりませんでした。

## 外部サービスとの連携

なし。パッケージには実行時の外部依存がありません。
パーサーは ECMAScript の組み込み機能（型付き配列、文字列、Unicode プロパティエスケープを使う正規表現）だけを使い、Node.js のモジュールを使わないので、[Requirements](requirements.ja.md#サーバーなしでパースする) が求めるとおり、そのままブラウザで動きます。
名前付き文字参照の表は、`tools/generate-entities.mjs` で [WHATWG の entities.json](https://html.spec.whatwg.org/entities.json) から生成し、ソースとしてコミットしています。

## データの扱い

なし。ソーステキストは `parse` が返った後は保持しません。ただし、再利用するプールは確保した容量を保ちます。

## 認証と認可

なし。パースにアクセス制御はありません。

## セキュリティの考慮事項

インラインのパースは CommonMark の区切り記号スタックと角括弧スタックのアルゴリズムを使います。これにより、閉じていない括弧や区切り記号で素朴なパーサーが遅くなる原因であるバックトラックを避けています。
Node.js 22 で以前の実装と比べた測定値は次のとおりです。

| 入力 | 以前 | 新しい実装 |
| --- | --- | --- |
| 20,000 行のテーブル | 約 25 秒 | 約 40 ms |
| 20,000 個の `[` の後に 20,000 個の `]` | 約 24 秒 | 約 12 ms |
| 20,000 個の `[a](` | 約 11 秒 | 約 33 ms |
| 1,000 段の入れ子のリスト | 約 24 秒 | 約 0.9 秒 |

入れ子のリストは、入れ子の深さに対して今も線形より速く時間が増えます。
数千段の入れ子の引用や強調の区切り記号は、両方の実装でコールスタックがあふれます（[Requirements](requirements.ja.md#未解決事項) の未解決事項を参照）。
例外を投げたパースの後でも、次の `parse()` の呼び出しがプールの状態をリセットします。

## デプロイの注意

この変更は、そのバージョンのほかの Markdown の AST の変更と一緒に、メジャーバージョンでリリースします。
リリースノートには、隠しプロパティ `position` の削除、ノードの種類の名前の変更、[互換性の差](#以前の実装との互換性)を記載します。

## 検討した代替案

### remark を使い続ける

remark のエコシステムに追従し続けられ、`remark-cjk-friendly` のような remark のプラグインも使えます。
remark は変換や書き出しも扱う汎用の Markdown 処理系ですが、textlint が使うのはそのパーサーだけで、結果を独自の AST に変換しています。
依存、位置の回避策、上で述べた遅いケースが残るので、採用しませんでした。

### micromark と mdast-util-from-markdown を直接使う

unified/remark の層をなくし、mdast を変換するときに `children` だけをたどり、トークナイザーには micromark を使い続ける案です。
外部パッケージは 134 個から 65 個（npm で新規にインストールした場合）に、パースの時間は約 18%（330 KB で 686 ms から 561 ms）に減り、AST は Pandoc 形式のインライン注を除いて同じです。インライン注には `remark-footnotes` が必要です。
残りの時間の大半を占める micromark のトークナイザーとその位置の不具合が残る一方、独自のパーサーは同じ 330 KB を約 10 ms でパースするので、採用しませんでした。

### 独自のパーサーを保守する（採用）

textlint が約 3,500 行のパーサーのコードを保守し、今後の CommonMark と GFM の変更に追従するのも textlint の仕事になる、というコストがあります。
仕様とその例のテスト一式によって挙動をテストでき、textlint には記載した拡張以外に独自に足す構文がないので、このコストを受け入れます。

## 未解決事項

- **CJK に配慮した強調：** textlint/textlint#2113 は `remark-cjk-friendly` を使うオプトインのオプションを提案している。この設計では、[markdown-cjk-friendly の仕様](https://github.com/tats-u/markdown-cjk-friendly)に従ってインラインフェーズに実装する必要があり、`parse` にオプションの引数が必要になる。先に Requirements での判断が必要。azu が PR の作者と決める。
- **タブに関係する range の差：** タブを含む入れ子のコンテナー内の末尾の空白で生じる、いくつかの `range` の差の原因は分かっていない。分かるまでは既知の差として扱う。そのような文書で位置が違うと利用者から報告があったときに調査する。
