# Markdown のパースの設計

[English](design.md)

## この文書について

この設計は、`@textlint/markdown-to-ast` が [textlint の Product](../../product.ja.md) の [Markdown のパースの Requirements](requirements.ja.md) をどう満たすかを説明します。
作られるノードは [TxtAST の Requirements](../txtast/requirements.ja.md) に従います。

### 読者

`@textlint/markdown-to-ast` または `@textlint/textlint-plugin-markdown` を変更する人とエージェント。

### 前提知識

- [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)、とくにその [parsing strategy](https://spec.commonmark.org/0.31.2/#appendix-a-parsing-strategy) と、[GFM](https://github.github.com/gfm/)
- [TxtAST の Requirements](../txtast/requirements.ja.md)

### この文書の範囲外

ルールが TxtAST をたどる方法と、プレーンテキストのパーサー。

## 実装の方針

このパッケージは、TxtAST を直接作る独自の CommonMark + GFM パーサーを持ちます。
textlint が必要とするのは Markdown の処理系のうちパースの部分だけなので、パッケージは汎用のフレームワークに依存せず、あとで変換する中間の AST も作りません。

設計は 3 つの考えに従います。

- **1 つのソース文字列と、すべてをオフセットで。** パーサーは、パースの間にテキストをコピーしたり書き換えたりしない。途中の値はすべてソースへのオフセットなので、`range` は作り方から正確であり、`raw` は最後に 1 回切り出すだけである。
- **データは平らな配列に。** ノード、行、スタックは、番号で引く型付き配列である。結果を組み立てるまで、ノードごとのオブジェクトは作らない。
- **各文字を見る回数に上限がある。** どの処理も、候補ごとに同じテキストを走査し直さないので、時間は大きさに比例する。

パースは、ブロック、インライン、出力の 3 つのフェーズで進みます。

### 準備

`parse` は BOM を取り除き、そのあとパーサーは 2 つのものを準備します。

1 つ目は、認識の対象にするテキストです。
テキストに U+0000 があるとき、パーサーはそれを U+FFFD に置き換えたコピーの上で動きます。
置き換えは長さを変えないので、オフセットはどちらでも同じであり、`raw` は元のテキストから切り出します。

2 つ目は行の表です。すべての行の開始オフセットを、`\n`、`\r\n`、`\r` を探す 1 回の走査で作ります。
ブロックフェーズはこの表を順にたどり、出力フェーズはこの表でオフセットを `loc` に変えます。

### ノードプール

3 つのフェーズは 1 つのノードプールを共有します。
プールは「配列の構造体」です。ノードの各フィールドが型付き配列であり、ノードは番号です。

| フィールド | 内容 |
| --- | --- |
| kind | 小さな整数で表したノードの種類 |
| start、end | ソースでのオフセット |
| 親、最初の子、最後の子、前の兄弟、次の兄弟 | ほかのノードの番号 |
| 4 つのペイロード | 意味は種類による。見出しの深さ、リストの開始番号、チェックの状態、サイドテーブルへの番号など |

サイドテーブルは、数値でない値のための通常の配列です。エスケープを含む `url` や `value` のようなデコードした文字列と、表の `align` の配列が入ります。
`value` が `raw` と等しい `Str` はサイドテーブルに入らず、その `value` は `raw` と同じ切り出しです。

木はリンクでつないだ構造なので、インラインフェーズは、データを動かさずに番号をつなぎ替えるだけで、既存のノードを `Emphasis` のような新しい親で包めます。

### ブロックフェーズ

ブロックフェーズは、CommonMark の parsing strategy の第 1 フェーズに従います。
テキストを 1 行ずつ読み、`Document` の下の開いているコンテナのスタックを持ちます。

各行について、次のことをします。

1. **開いているコンテナを続ける。** 外側から順に、開いているコンテナが、その行が自分を続けるかどうかを調べる。引用は `>` を必要とし、リストの項目と脚注の定義は自分のインデントを必要とする。タブは、テキストを書き換えずに列として数える。
2. **開いているリーフを続けるか、閉じる。** すべてのコンテナが一致したとき、開いているリーフが、その行が自分に属するかどうかを決める。フェンスコードブロックは終了のフェンスまで、HTML ブロックは終了条件まで、などである。コンテナが一致せず、開いているリーフが段落のとき、その行はマーカーを省いた継続行でありうる。
3. **新しいブロックを開く。** そうでなければ、パーサーはインデントのあとの最初の文字を見て、その文字で始まりうるブロックの開始を試す。引用のマーカー、ATX 見出し、コードのフェンス、HTML ブロック、Setext の下線、区切り線、リストの項目、表の区切り行、脚注の定義である。4 列以上インデントした行は、代わりにインデントコードを始める。コンテナの開始は、行の残りについてこの手順を繰り返す。
4. **行をリーフに加える。** 行の残りは新しい段落になるか、開いている段落を続ける。

ブロックの開始が段落を中断できるかどうかは、手順 3 で 1 つのフラグによって決めます。フラグは、その行がそうでなければ段落の継続テキストになるかどうかを表します。
このフラグが、空のリストの項目、1 で始まらない順序付きリスト、HTML ブロックの開始条件 7 が、マーカーを省いた継続行を含めて段落を中断しない、という決まりを実装します。

リーフは自分の行をコピーしません。
行をセグメントとして記録します。セグメントは、コンテナのマーカーとインデントを除いたあとの開始と終了のオフセットの組です。
インラインフェーズが読むのは、このセグメントです。

段落が閉じるとき、パーサーは段落の先頭からリンク参照定義を取り出し、それぞれが `Definition` ノードになります。
定義は正規化したラベルで登録し、同じラベルでは最初の定義が有効です。

表は、開いている段落の最後の行のあとに区切り行が続き、セルの数が一致するときに始まります。
最後の行が見出し行になり、その前の行は段落のまま残ります。
セルはエスケープされていない `|` で分け、各セルは内容のセグメントを記録します。

タスクリストのマーカーは、リストの項目の最初の段落でインラインフェーズが始まるときに認識します。
チェックの状態は `ListItem` に入り、段落の開始はマーカーとそのあとの空白の後ろに移ります。

フロントマターは、行のループの前に、最初の行で 1 回だけ試します。
終了のフェンスが見つからなければ、何も試さなかったかのように、行のループは最初の行から始まります。

開いているコンテナが入れ子の上限に達したとき、手順 3 は次のコンテナを開かず、マーカーは現在のブロックのテキストとして扱います。

### インラインフェーズ

インラインフェーズは、CommonMark の parsing strategy の第 2 フェーズに従います。
インラインの内容を持つすべてのリーフを訪れます。段落、見出し、表のセル、インラインの注の内容です。

**バッファ。** 1 行のリーフは、ソースの上でそのままパースします。
複数行のリーフは、セグメントを `\n` でつないだバッファを通してパースします。行の間にあるコンテナのマーカーとインデントが、内容として見えないようにするためです。
バッファは各行の開始を持ち、バッファでの位置は、ノードを仕上げるときにソースのオフセットに戻します。
結果を組み立てる前にテキストをコピーするのは、ここだけです。

**走査。** パーサーはバッファを進み、構文を始めうる文字でだけ止まります。
その間のテキストは `Str` ノードになります。

| 文字 | 構文 |
| --- | --- |
| `` ` `` | コードスパン |
| `\` | エスケープ、または改行の前の強制改行 |
| `&` | 文字参照 |
| `<` | 自動リンクまたは生の HTML |
| `[`、`![` | リンク、画像、脚注の参照のための角括弧を開く |
| `]` | いちばん近い角括弧、またはいちばん近いインラインの注を閉じる |
| `^[` | インラインの注を開く |
| `*`、`_`、`~` | 区切り文字の並び |
| 改行 | 2 つ以上のスペースが前にあるとき、強制改行 |
| `www.`、`http://`、`https://`、メールアドレスの始まり | 自動リンクのリテラル |

**角括弧。** `[` と `![` は角括弧のスタックに積みます。
`]` では、パーサーはいちばん近い角括弧を見て、インラインリンク、full または collapsed の参照、shortcut の参照を順に試します。
リンクを作るとき、その中の区切り文字を先に解決し、それより前の `[` の角括弧を無効にします。リンクはリンクを含まないからです。

**区切り文字。** `*`、`_`、`~` の並びは、長さと、開けるか閉じられるかとともに、区切り文字のスタックに積みます。
区切り文字は、元のテキストの順に 1 回の走査で解決します。閉じる側はそれぞれ、対応できるいちばん近い開く側を取り、その組が `Emphasis`、`Strong`、`Delete` になり、組の間の区切り文字は取り除きます。
1 回の走査が 3 つの文字をすべて扱うので、組は交差しません。

**CJK に配慮した強調。** `cjkFriendlyEmphasis` が `true` のときに変わるのは、並びが開けるか閉じられるかの判断だけです。そのため、区切り文字のスタックとその解決は既定と共通です。
判断には、並びのまわりの文字をコードポイントとして使います。
並びの前では、サロゲートペアをつなげて 1 つのコードポイントを読みます。それが絵文字でない汎用の異体字セレクター（U+FE00 から U+FE0E）のときは、その前のコードポイントも読みます。仕様は、文字とその異体字セレクターを 1 つの並びとして分類するからです。
並びの後では、1 つのコードポイントを読みます。
判断の順は [実装者向けのヒント](https://github.com/tats-u/markdown-cjk-friendly/blob/main/implementers-tips.md) に従います。

1. どちらかの側が空白のとき、結果は CJK の文字に依存しないので、CommonMark と同じように判断します。
2. `_` でも、結果は CJK の文字に依存しません。異体字の並びの基底の文字を並びの前の文字として、CommonMark と同じように判断します。
3. `*` と `~` では、どちらかの側が CJK の文字かどうかを調べます。並びは、後ろが空白でなく、かつ「後ろが句読点でない」「前が空白か句読点である」「どちらかの側が CJK である」のいずれかを満たすとき、left-flanking です。right-flanking かどうかは、前後を入れ替えて同じように決めます。並びの前では、漢字の異体字セレクターと CJK の曖昧な句読点の並びも CJK として数えます。

文字が CJK かどうかは、コードポイントの範囲の表を二分探索して決めます。
表は仕様が公開する範囲から生成するので、すでに絵文字を除いており、パーサーは実行時に East Asian Width のデータを必要としません。

**仕上げ。** 走査のあと、隣り合うテキストを 1 つの `Str` にまとめ、バッファでの位置をソースのオフセットに戻し、デコードが必要な値をサイドテーブルに入れます。

### 出力フェーズ

出力フェーズは、プールを `Document` から 1 回たどり、`TxtNode` のオブジェクトを作ります。
ノードは、種類ごとに決まった順のプロパティを持つプレーンなオブジェクトです。
`raw` は元のテキストから切り出し、`loc` は行の表から求めます。
ノードは元のテキストの順に訪れるので、開始オフセットの行は、表を探索せずに、前のノードの行から続けて求めます。

拡張が有効なとき、`Document` は最後のプロパティとして `syntaxExtensions` を持ち、そこには有効な拡張ごとにキーがあります。
どれも有効でないとき、パーサーはこのプロパティを加えないので、オブジェクトはオプションなしのときと同じです。

ノードは、最初からすべてのプロパティを持つ形で作ります。
ルールはどのノードのどのプロパティも読むことがあり、プレーンなオブジェクトは、TxtAST が求めるとおり AST をシリアライズできる状態に保ちます。

### 呼び出しの間の状態

プール、行の表、スタックはモジュールのレベルにあり、次の `parse` の呼び出しが再利用します。そのため、呼び出しのたびに確保し直しません。
どの呼び出しも、始めにカウンターをリセットし、ノードを割り当てるときにそのノードのすべてのフィールドを設定します。そのため、呼び出しが前の文書のデータを読むことはありません。
定義とサイドテーブルは、呼び出しごとに作ります。
オプションは、呼び出しのたびに始めにモジュールのレベルのフラグに読み込みます。そのため、呼び出しが前の呼び出しのオプションを使うことはありません。
`parse` が返るとき、または例外を投げるとき、テキストへの参照を手放します。

## アーキテクチャとシーケンス図

図は必要ありません。`parse` は 3 つのフェーズを順に呼び、どのフェーズも、文字参照の表を除いてほかのモジュールを呼びません。

## データモデルと ER 図

出力は [TxtAST の Requirements](../txtast/requirements.ja.md) が定義する木であり、ノードは [Markdown のパースの Requirements](requirements.ja.md#機能要件) に載っています。

内部のデータは、[実装の方針](#実装の方針) で説明した、ノードプール、サイドテーブル、行の表、セグメントです。
どれも外には公開しません。

## API とインターフェース

関数は `parse(text: string, options?: ParseOptions): TxtDocumentNode` だけであり、`Syntax` は `ASTNodeTypes` を再エクスポートします。
`ParseOptions` は型としてエクスポートし、`cjkFriendlyEmphasis?: boolean` を持ちます。
`parse` は、どんなテキストやオプションに対しても例外を投げません。

`@textlint/textlint-plugin-markdown` は、プラグインのオプションから `cjkFriendlyEmphasis` を読んで `parse` に渡し、ほかのプラグインのオプションは渡しません。
プロセッサーがオプションを保持するので、修正の後のパースは最初のパースと同じオプションを使います。

`@textlint/ast-node-types` の `TxtDocumentNode` は、[TxtAST の Requirements](../txtast/requirements.ja.md#文書の拡張) が定義するとおり、`syntaxExtensions?: { readonly [name: string]: unknown }` を持ちます。
ルールは、`Document` のハンドラーで、または `parent` をたどったルートから、`node.syntaxExtensions?.cjkFriendlyEmphasis === true` として読みます。

ノードは、TxtAST の共通のプロパティと、そのノードの種類のプロパティだけを持ちます。

## 外部サービスとの連携

なし。このパッケージは、実行時にサードパーティのパッケージに依存しません。
パーサーは ECMAScript の組み込み（型付き配列、文字列、Unicode プロパティエスケープを使う正規表現）だけを使い、Node.js のモジュールを使いません。そのため、[Requirements](requirements.ja.md#サーバーなしでパースする) が求めるとおり、そのままブラウザで動きます。
名前付き文字参照の表は、パッケージ内のスクリプトで [WHATWG の entities.json](https://html.spec.whatwg.org/entities.json) から生成し、ソースとしてコミットします。そのため、実行時にデータを取得しません。
CJK の文字の表も、同じように [CJK に配慮した仕様の範囲](https://github.com/tats-u/markdown-cjk-friendly/blob/main/ranges.md) から生成します。

## データの扱い

なし。ソーステキストは `parse` が返った後は保持しません。ただし、再利用するプールは確保した容量を保ちます。

## 認証と認可の注意

なし。パースにアクセス制御はありません。

## セキュリティの考慮事項

[Requirements のセキュリティの考慮事項](requirements.ja.md#セキュリティの考慮事項) は、細工された文書がパースを止めず、コールスタックもあふれさせないことを求めています。

### 大きさに比例する時間

ブロックフェーズは、各行を開いているコンテナごとに 1 回訪れます。コンテナの数は入れ子の上限で抑えられます。

インラインフェーズは、CommonMark の区切り文字のスタックと角括弧のスタックを使います。これらは、閉じていない角括弧と区切り文字を、走査し直さずに扱います。
区切り文字の探索は、閉じる側の種類ごとに、開く側が見つからないまますでに探した範囲を覚えます。そのため、あとの閉じる側が同じ範囲をもう一度探すことはありません。

閉じる部分が遠くにあるか、存在しないかもしれない構文があります。
候補がそれぞれ自分の閉じる部分を探すと、多くの候補が同じテキストを何度も走査することになります。
このような構文では、パーサーは現在のバッファについて走査の結果を覚えます。

| 候補 | 覚えるもの |
| --- | --- |
| バッククォートの並び | 長さごとの、最後の並びの位置。バッファの 1 回の走査で求める |
| `<!--`、`<?`、`<!X`、`<![CDATA[` | ある位置より後ろに、この種類の終端がないこと |
| 丸括弧のリンクタイトル | 最後の走査が覆った範囲と、それが終わった位置 |
| 自動リンクのリテラルの末尾の記号 | 最後の走査が覆った並びと、その結果 |

CJK に配慮した強調では、区切り文字の並びは前の 2 つまでのコードポイントと後ろの 1 つのコードポイントを読み、表の探索は決まった回数で終わります。そのため、この拡張が加える処理は並びごとに一定です。

### 深さの上限

入れ子の深さは文書が決めるので、パーサーは 100 段の固定の上限で抑えます。上限は、ブロックとインラインに別々に適用します。

ブロックでは、`Document` の下の開いているコンテナのスタックが、上限を超えて伸びることはありません。

インラインでは、上限は区切り文字の数ではなく、インラインの部分木の高さに適用します。
各ノードは、作られるときに自分の部分木の高さを記録します。
ノードを上限より高くすることになる区切り文字や角括弧の組は対応させないので、内側の段は保たれ、外側のマーカーはテキストのまま残ります。
ある位置で上限に達すると、探索はその位置より前には戻りません。それより前の開く側は、同じ深い内容を包むことになるからです。

ブロックとインラインを別々に制限するので、もっとも深い AST は、`Document`、100 段のコンテナ、`Paragraph` または `TableCell`、100 段のインライン、`Str` です。

### 深さに対して再帰しない

どのフェーズも、入れ子の深さに対して再帰しません。
深さが木に従う処理、つまりインラインの仕上げ、画像の説明のテキストの収集、出力フェーズは、親へのリンクまたは明示的なスタックを使います。
上限だけでも再帰は安全ですが、ループにしておけば、上限が変わってもパーサーは安全です。

### 独立した呼び出し

`parse` が例外を投げても、次の `parse` の呼び出しが共有の状態をリセットするので、失敗は後の文書に影響しません。

## デプロイの注意

ノードの種類、ノードのプロパティ、位置の変更は、それに依存するルールを壊します。そのため、そのような変更はメジャーバージョンでだけリリースし、変更点をリリースノートに載せます。

拡張は既定で無効であり、オプションなしの AST を変えないので、拡張の追加はマイナーバージョンでリリースします。
CJK に配慮した仕様の新しい版のように、拡張によるテキストの認識を変えると、それを使う文書の AST が変わるので、メジャーバージョンでリリースします。

## 検討した代替案

### remark を使う

remark には大きなエコシステムがあり、そのプラグインで構文を追加できます。
remark は変換と書き出しも扱う汎用の Markdown の処理系ですが、textlint はパースだけを使い、結果を独自の AST に変換します。
次の 3 つの理由で採用しませんでした。
textlint が使わないパッケージを持ち込みます。
その AST には位置を持たないノードがあるので、TxtAST への変換に回避策が必要です。
細かい場合の挙動を実装が決めるので、textlint は AST を自分の Requirements に従わせることができません。

### micromark と mdast-util-from-markdown を直接使う

これはフレームワークの層をなくし、トークナイザーを残します（[#2187](https://github.com/textlint/textlint/pull/2187)）。
トークナイザーと、その AST からの変換が残り、位置と挙動についての同じ制約も残るので、採用しませんでした。

### 自前のパーサーを保守する（採用）

代償は、textlint が独自のパーサーを保守し、今後の CommonMark と GFM の変更に自分で追従することです。
これを受け入れるのは、CommonMark と GFM が例の一式を持つ書かれた仕様であり、挙動をテストできるからです。また、textlint には、Requirements に載っている拡張のほかに追加する独自の構文がありません。

### `loc` と `raw` を最初に読まれたときに作る

ルールが `raw` と `loc` を読むノードは少ないので、読まれたときにだけ作れば、出力フェーズの仕事が減ります。
採用しなかったのは、プロトタイプ上の getter が必要になり、ノードがプレーンなデータと異なるものになるからです。ノードはそのままではシリアライズされず、ノードをコピーするカーネルやツールには別のオブジェクトに見えます。
減る時間は、Lint の実行全体の時間と比べて小さいものです。

### 打ち消し線を強調とは別に解決する

`~` を独自の走査で解決するのは単純です。打ち消し線には 3 の倍数の決まりがないからです。
採用しなかったのは、走査を 2 回にすると組が交差でき、結果が元のテキストの順ではなく、どちらの走査を先に実行するかで決まるからです。

### remark と remark-cjk-friendly を使う

[#2113](https://github.com/textlint/textlint/pull/2113) は、remark のプラグインで CJK に配慮した強調を加えます。
採用しなかったのは、[remark を使う](#remark-を使う) に書いた理由で、パーサーがもう remark を使わないからです。

### ルールごとにオプションを持たせる

ja-space-around-strong のようなルールは、[textlint-rule-preset-ja-spacing#144](https://github.com/textlint-ja/textlint-rule-preset-ja-spacing/pull/144) の `cjkFriendly` のように、自分のオプションを持てます。
採用しなかったのは、書き手が同じ選択をプラグインとすべてのルールに設定することになり、オプションがパーサーと食い違ったルールは、AST にない認識に基づいてテキストを修正するからです。

### すべてのルールが読める設定を加える

textlint には、すべてのルールで共有する設定がなく、ルールはプラグインのオプションを読めません。
共有の設定を加えると、1 つのフラグのために設定とカーネルが変わり、その設定もパーサーと一致させる必要が残ります。
拡張を AST に記録すれば、情報源は AST を作ったパーサーの 1 つになります。

### 拡張ごとに `Document` のプロパティを持たせる

`Document.cjkFriendlyEmphasis` のほうが短く読めます。
採用しなかったのは、拡張ごとにルートのプロパティが増え、ルールが文書のパースのされ方を 1 か所から知ることができないからです。

### 無効な拡張を `false` として記録する

すべての文書に `{ "cjkFriendlyEmphasis": false }` を書くと、既定値が明示されます。
採用しなかったのは、すべての文書の AST が変わる一方で、ルールはどちらでも `=== true` で調べるからです。

### プロパティの名前を `extensions` にする

`extensions` のほうが短い名前です。
採用しなかったのは、プラグインにはファイルの拡張子を表す `extensions` オプションがすでにあり、TxtAST には拡張ノードもあるので、同じ言葉が 3 つの意味を持つことになるからです。

### 拡張を名前の配列として記録する

`["cjkFriendlyEmphasis"]` もシリアライズできます。
オブジェクトを選んだのは、ルールが探索せずに 1 つのキーを読め、将来の拡張が `true` 以外の値を持てるからです。

### East Asian Width のデータで CJK の文字を決める

markdown-it-cjk-friendly が使う `get-east-asian-width` のようなパッケージは、コードポイントごとの幅を返します。
採用しなかったのは、実行時の依存が増え、仕様が絵文字を除いた結果の範囲を公開しているからです。

### 木を再帰でたどる

再帰でたどる処理は短く書け、入れ子の上限がその深さを抑えます。
採用しなかったのは、パーサーの安全性が上限の値に依存することになるからです。
