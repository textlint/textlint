# Markdown のパース

[English](requirements.md)

## この文書について

Markdown のパースは、Markdown のテキストを TxtAST に変換し、ルールが文章をチェックして正確な位置を報告できるようにします。
Markdown には仕様があるので、その構文はノードとしてパースし、中にある自然言語はルールが扱うテキストとして残します。
`@textlint/markdown-to-ast` が提供し、組み込みの `@textlint/textlint-plugin-markdown` が使います。
親の Product は [textlint](../../product.ja.md) です。

### 範囲

- `parse(text)` 関数と、それが生成するノードの種類
- どの Markdown 構文をノードにし、どれをテキストのまま残すか
- すべてのノードの位置情報（`range`、`loc`、`raw`）
- パースの速度と、パースに必要な依存

### 範囲外

- プレーンテキストのパースと、プラグインが提供するその他の形式
- 文章を文や単語に分割すること。これはルールが、たとえば文分割ライブラリや形態素解析器を使って行う
- Markdown を HTML に変換すること、AST から Markdown を書き戻すこと
- ルールが AST をどう使うか、および TxtAST の正式な仕様（[Product](../../product.ja.md) の未解決事項を参照）

## ユーザーストーリー

### 文章だけをチェックする

書き手として、Markdown の構文が構文として認識されてほしい。そうすれば、ルールは自分の文をチェックし、マークアップに対して誤検知を出さない。
リンク、コード、フロントマターのように意味のある構文は、文字列に残らずノードになる。

**受け入れ条件：**

シナリオ：文にインラインの構文が含まれるとき、構文はノードになり、文章は `Str` に残る

- Given：段落 `See [docs](https://example.com) and \`code\`.`
- When：テキストをパースする
- Then：段落の子は `Str`、`Link`、`Str`、`Code`、`Str` で、URL はどの `Str` にも含まれない

シナリオ：文書がフロントマターで始まるとき、フロントマターは 1 つのノードになる

- Given：`---` で囲まれた YAML のブロックで始まる文書
- When：テキストをパースする
- Then：`Document` の最初の子は `yaml` ノードで、その `raw` は囲まれたブロック全体であり、YAML を含む `Str` はない

シナリオ：テキストが有効な Markdown の構文でないとき、テキストのまま残る

- Given：段落 `a * b * c`
- When：テキストをパースする
- Then：段落は `Str` だけを含み、パースは例外を投げない

### 正しい位置を報告する

ルール作者として、すべてのノードがソースの正確なテキストを指してほしい。そうすれば、エラーと修正が正しい文字に適用される。

**受け入れ条件：**

シナリオ：どのノードでも、`raw` が `range` と一致する

- Given：任意の Markdown のテキスト
- When：テキストをパースする
- Then：すべてのノードで `raw` は `text.slice(range[0], range[1])` と等しく、`loc` は `range` と同じ範囲を表す

シナリオ：テキストが BOM で始まるとき、位置は BOM を数えない

- Given：U+FEFF で始まるテキスト
- When：テキストをパースする
- Then：`range` と `loc` は、BOM のないテキストの場合と同じになる

シナリオ：ノードが入れ子になっているとき、子は親の内側にある

- Given：引用の中のリストのような入れ子のコンテナー
- When：テキストをパースする
- Then：各子の `range` は親の `range` の内側にあり、兄弟同士は重ならない

### 既存のルールを動かし続ける

ルール作者として、ノードの種類と形が安定していてほしい。そうすれば、textlint がパーサーを更新しても、公開済みのルールが動き続ける。

**受け入れ条件：**

シナリオ：一般的な Markdown を使う文書では、ノードの種類は `@textlint/ast-node-types` に従う

- Given：見出し、リスト、引用、コードブロック、強調、リンク、画像を含む文書
- When：テキストをパースする
- Then：ノードの種類は `ASTNodeTypes` の名前（`Header`、`List`、`ListItem`、`BlockQuote`、`CodeBlock`、`Emphasis`、`Strong`、`Link`、`Image` など）になる

シナリオ：パーサーの実装が変わっても、既存のフィクスチャは同じ AST を生成する

- Given：`packages/@textlint/markdown-to-ast/test/fixtures` にあるフィクスチャ
- When：新しい実装でパースする
- Then：出力はコミット済みの `output.json` と等しい。ただし、リリースノートに破壊的変更として記載した変更は除く

### サーバーなしでパースする

組み込む開発者として、パーサーがブラウザで動いてほしい。そうすれば、書き手のテキストをチェックのためにサーバーへ送らずに済む。

**受け入れ条件：**

シナリオ：パーサーをブラウザ向けにバンドルするとき、Node.js の polyfill を必要としない

- Given：`@textlint/markdown-to-ast` とその実行時の依存を、各パッケージの `browser` 条件で解決したもの
- When：ブラウザ向けにバンドルする
- Then：バンドルは `node:fs` や `node:util` のような Node.js の組み込みモジュールを必要とせず、`parse` は Node.js と同じ AST を返す

## KPI

### パースの速度

- **現在の値：** 実在する `.md` ファイル 3,189 件（15.3 MB）で約 0.8 MB/s（18,506 ms、中央値）。このリポジトリの Markdown 330 KB で約 657〜686 ms。
- **目標値：** 同じコーパスで現在の値より遅くならないこと。速いほうが望ましい。
- **測定方法：** 実際の文書からなる同じコーパスを Node.js 22 でループしてパースし、現在の実装と新しい実装の中央値を比べる。
- **測定時期：** パーサーの実装を変えるとき。

### 依存

- **現在の値：** `pnpm-lock.yaml` から計算した、`@textlint/markdown-to-ast` の本番依存の閉包にある外部パッケージ 96 個（7.5 MB）。
- **目標値：** 現在の値より少ないこと。Markdown の書き出しのように、パース以外の処理にしか使わないパッケージは必要ない。
- **測定方法：** `pnpm-lock.yaml` から本番依存の閉包を数える。
- **測定時期：** パッケージの依存を変えるとき。

## 機能要件

### Markdown を TxtAST にパースする

**概要：** `parse(text)` はテキスト全体を含む `Document` ノードを返す。

**入力：** Markdown の文字列。BOM で始まってもよい。

**出力：** `TxtDocumentNode`。すべてのノードは `type`、`raw`、`range`、`loc` を持つ。テキストのノードは `value` も持つ。

#### 適用条件

##### 対応する構文

- CommonMark 0.31.2
- GFM：テーブル、取り消し線、タスクリスト、自動リンク（`https://…`、`www.…`、メールアドレスは `Link` になる）、脚注（`[^1]` と `[^1]: …`）
- Pandoc 形式のインライン注（`^[note]`）
- 文書の先頭のフロントマター：YAML（`---`）、TOML（`+++`）、JSON（`;;;`、`---json` … `---`、または `{` … `}`）

##### ノードの種類

- `ASTNodeTypes` に対応があるノードは、その PascalCase の名前を使う。`Table`、`TableRow`、`TableCell`、`LinkReference`、`ImageReference`、`Definition` もこれに含まれる。
- `ASTNodeTypes` にない Markdown 固有のノードは小文字の名前を使う：`yaml`、`toml`、`json`（フロントマター）、`footnoteReference`、`footnoteDefinition`、`footnote`（インライン注）。フロントマターも脚注も、CommonMark と GFM の仕様には含まれない。
- 生の HTML は、ブロックでもインラインでも `Html` になる。

##### 位置

- `range` は、BOM を除いたテキスト中のオフセットの組である。
- `loc` の行は 1 から、列は 0 から数える。

#### 例外的な挙動

##### 不正な Markdown

Markdown に構文エラーはない。閉じていない構文や無効な構文は CommonMark に従ってテキストになり、`parse` は例外を投げない。

##### 閉じていないフロントマター

フロントマターの区切りが閉じていないとき、テキストは最初の行から通常の Markdown としてパースされる。

## データ要件

### 必要なデータ

- **ソーステキスト：** `parse` に渡された Markdown の文字列。`parse` が返った後は保持しない。

### 関係

`Document` 以外のノードはちょうど 1 つの親を持ち、ノードの子はソース上の順に並ぶ。

### 個人情報

なし。パーサーはデータを収集も保持もしない。

## 外部サービスへの依存

なし。パースはローカルで動き、ネットワークのサービスを使わない。

## セキュリティの考慮事項

textlint は CI で、信頼できない投稿者の文書に対しても実行されるので、細工された文書や珍しい文書でパースが止まってはならない。
長いテーブル、閉じていない大量の括弧、深く入れ子になったリストを含めて、パースの時間は入力の大きさにほぼ比例しなければならない。

## 未解決事項

- **パースの速度の数値目標：** 目標は当面「現在の値より遅くならないこと」とする。パーサーの実装が決まった後で数値目標を設定できる。azu が決める。
- **極端に深い入れ子：** 数千段の引用や強調の区切り記号があると、`parse` は `RangeError: Maximum call stack size exceeded` を投げる。このような入力でも AST を返すかどうかは決まっていない。それまでは、エラーは呼び出し側に届く。azu が決める。
- **CJK に配慮した強調：** CJK の句読点の隣にある強調と取り消し線を認識するオプトインのオプションが textlint/textlint#2113 で提案されている。この機能の一部にするかどうかは決まっていない。それまでは、強調は CommonMark に従う。azu が PR の作者と決める。
