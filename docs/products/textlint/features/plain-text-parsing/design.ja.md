# プレーンテキストのパースの設計

[English](design.md)

## この文書について

この設計は、`@textlint/text-to-ast` が [textlint の Product](../../product.ja.md) の [プレーンテキストのパースの Requirements](requirements.ja.md) をどう満たすかを説明します。
出力するノードは [TxtAST の Requirements](../txtast/requirements.ja.md) に従います。

このパーサーは TxtAST のパーサーの例として読まれることを想定しているので、この設計は、小さな速度の向上よりも、Requirements のノードの表と 1 対 1 に対応するコードを優先します。

### 読者

`@textlint/text-to-ast` や `@textlint/textlint-plugin-text` を変更する人とエージェント、そしてパーサーを例として読むプラグインの作者。

### 前提知識

- [TxtAST の Requirements](../txtast/requirements.ja.md)。特に位置の規約

### この文書の範囲外

カーネルが TxtAST をたどり、メッセージのためにオフセットを行に変換する方法と、Markdown のパーサー。

## 実装の方針

`parse` はテキストを行から行へと 1 回だけたどり、各ノードにたどり着いたときにそのノードを作ります。
行の中間的なリストも、ノードに対する 2 回目の走査もありません。

### 準備

`parse` はテキストの先頭の BOM を取り除きます。
それ以降、すべてのオフセットは BOM のないテキストを指し、`Document` の `raw` はそのテキストです。

### 行のループ

ループは 2 つの値を持ちます。現在の行が始まるオフセットと、1 から始まる現在の行番号です。
各ステップでは、次のことを行います。

1. **改行を探す。** パーサーは、Requirements の改行を並べた 1 つの正規表現 `/\r\n|[\n\r]/g` で次の改行を探します。`\r\n` が最初の選択肢なので、`\r` と `\n` の 2 つではなく、1 つの改行として見つかります。行は改行が始まる位置で終わります。
2. **段落を加える。** 行が空でないとき、パーサーはその行の `Paragraph` を、1 つの `Str` とともに加えます。
3. **改行を加える。** パーサーは改行の `Break` を加え、次の行はその後から始まります。

改行が残っていないときは、テキストの残りが改行を持たない最後の行で、それが空でなければ、パーサーはその `Paragraph` を加えます。
ステップ 1 で見つけたすべての改行がステップ 3 で `Break` になるので、空行の改行とテキストの末尾の改行も、ほかの改行と同じように扱われます。
正規表現は呼び出しごとに作るので、検索の位置が呼び出しの間で共有されることはありません。

### 位置

ノードは行をまたがないので、その `loc` はループから直接決まります。
`Paragraph` とその `Str` は現在の行の 0 列目から始まり、行の長さの列で終わります。
`Break` はその列から始まり、次の行の 0 列目で終わります。TxtAST の位置の規約が、改行の直後で終わる範囲にそれを求めているからです。

`Document` の終わりは、現在の行と、その行の中でのテキストの終わりの列です。ループはそれを、終わるときに知っています。
テキストが改行で終わるときは、その次の行の 0 列目になります。

### ノード

各ノードは、決まった順にプロパティを持つプレーンなオブジェクトリテラルです。順は `type`、`raw`、`Str` では `value`、`range`、`loc`、親ノードでは `children` です。
`raw` はテキストから切り出し、`Str` の `value` はその `raw` と同じ文字列です。
ノードの種類ごとに小さな関数があるので、Requirements のノードの表の各行が 1 つの関数に対応します。

## アーキテクチャとシーケンス図

図は必要ありません。`parse` は 1 つのループを持つ 1 つの関数で、プラグインは `preProcess` からそれを呼びます。

## データモデルと ER 図

出力は [TxtAST の Requirements](../txtast/requirements.ja.md) が定義する木で、ノードは [プレーンテキストのパースの Requirements](requirements.ja.md#ノード) に挙げたものです。
パーサーは、ループの 2 つの値のほかに内部のデータを持ちません。

## API とインターフェース

### パーサー

`parse(text: string): TxtDocumentNode` が唯一の関数で、`Syntax` はそれが出力するノードの種類 `Document`、`Paragraph`、`Str`、`Break` を、`ASTNodeTypes` の値で挙げます。
`parse` はオプションを持たず、どの文字列に対しても例外を投げません。

### プラグイン

`@textlint/textlint-plugin-text` は `Processor` を公開します。
その `availableExtensions()` は、`.txt`、`.text`、そして `extensions` オプションの拡張子を返します。
`preProcess(text)` は `parse(text)` を返し、`postProcess(messages, filePath)` はメッセージをそのまま返します。ファイルのパスが渡されないときは、パスを `<text>` とします。

## 外部サービスとの連携

なし。パッケージはノードの種類のために `@textlint/ast-node-types` だけに依存し、ECMAScript の組み込みの機能だけを使うので、そのままブラウザーで動きます。

## データの扱い

なし。`parse` が返った後、テキストは保持しません。

## 認証と認可の注意

なし。パースにはアクセス制御がありません。

## セキュリティの考慮事項

[Requirements のセキュリティの考慮事項](requirements.ja.md#セキュリティの考慮事項) は、大きさに比例する時間と、上限のある深さを求めています。

ループの各ステップは前の改行の終わりから次の改行を探すので、各文字は 1 回だけ訪れます。正規表現は最大 2 文字にしか一致しないので、バックトラックしません。
AST の深さはノードの表で決まっていて、パーサーは再帰しません。
パーサーは呼び出しの外に状態を持たないので、呼び出しは独立しています。

## デプロイの注意

ノードの種類、ノードのプロパティ、位置の変更は、それに依存するルールを壊します。そのため、そのような変更はメジャーバージョンでだけリリースし、変更をリリースノートに載せます。

## 検討した代替案

### 先にテキストを行に分ける

正規表現でテキストを行の配列に分け、各行をノードに対応させる方法は、行を見つけることとノードを作ることを分けられます。
これを選ばなかったのは、配列が読み手の追うべき余分なデータ構造になり、改行のない最後の行に両方のステップで専用の場合分けが必要になるからです。
1 つのループでも同じくらい短く、すべての改行を同じ場所で扱えます。

### Markdown のパーサーの行の扱いを再利用する

Markdown のパーサーは、すでに行の表と、オフセットから `loc` を作る出力フェーズを持っています。
これを選ばなかったのは、プレーンテキストのパーサーが Markdown のパーサーの内部データに依存することになり、単独で読める小さな例ではなくなるからです。

### 1 文字ずつ改行かどうかを調べる

各文字のコードを読み、改行と比べるループにすれば、正規表現を使わずに済みます。
これを選ばなかったのは、ある位置の改行の長さを返す関数と、動かすための 2 つ目の添字が必要になるからです。正規表現なら改行の定義を 1 行で書け、テキストの走査はエンジンに任せられます。
