# 変更の比較

[English](requirements.md)

## この文書について

変更の比較は、textlint の 2 つのビルド、ベース（`master` など）とヘッド（プルリクエスト）を同じ文書で実行し、その差を示します。差とは、Lint 結果、CLI の実行時間、各パーサーとトラバースの時間、各ビルドのプロファイル、CPU 時間の使われ方です。
作者、AI エージェント、レビュアーが、パーサー、カーネル、そのほかのホットパスの変更の影響を、マージ前に見られるようにします。
比較は 1 つのスクリプトが行います。開発者と AI エージェントはローカルで実行し、CI はプルリクエストごとに同じスクリプトを実行して、出力をジョブサマリーに載せます。
親の Product は [textlint](../../product.ja.md) です。実行のフェーズ、パーサー、ルールは [パフォーマンスプロファイル](../performance-profile/requirements.ja.md) から得ます。

### 範囲

- 比較スクリプト：入力、使う文書のセット、Markdown、JSON、CPU プロファイルの出力
- CLI を通さないパーサーとトラバースの測定
- プルリクエスト（フォークからのものを含む）に対してスクリプトを実行する CI ジョブ
- AI エージェントにスクリプトを実行させ、出力をプルリクエストに載せさせる指示

### 範囲外

- 変更を受け入れるかの判断。比較は差を示し、人が判断する。
- 差を理由に CI を失敗させること。CI は結果を示し、それで失敗しない。
- プルリクエストへのコメント。この機能の出力の上に後から追加できる。
- `master` の実行時間の履歴を記録するベンチマーク（`ci.yml` の `benchmark` ジョブ）。
- ルールの速度。ルールは固定した現実的な負荷として使い、ルール自身の性能はそれぞれのリポジトリが扱う。

## ユーザーストーリー

### パーサーやカーネルの変更の影響を、プルリクエストを開く前に見る

パーサー、トラバース、そのほかのホットパスを変更する開発者や AI エージェントとして、自分のブランチを `master` と比べる 1 つのコマンドがほしい。差をプルリクエストの説明に載せられるようにするためです。

**受け入れ条件：**

シナリオ：ヘッドが Markdown のパーサーを速くしたとき、出力がそれをパーサーについて示す

- Given: ヘッドが `@textlint/markdown-to-ast` を速くパースするように変更し、ベースは `master`
- When: 開発者が medium のセットで比較スクリプトを実行する
- Then: Markdown の出力は、ベースとヘッドの Markdown のパーサーの時間とその比、各ビルドで CPU 時間をもっとも使うパーサーの関数を示す

シナリオ：ヘッドが Lint 結果を変えたとき、出力は変わったメッセージを列挙する

- Given: ヘッドがパーサーを変更し、ルールが別の列でメッセージを報告するようになった
- When: 開発者が比較スクリプトを実行する
- Then: 出力は Lint 結果が変わったことを示し、削除されたメッセージと追加されたメッセージを、ルール ID、ファイル、行、列、メッセージで列挙する

シナリオ：ヘッドが Lint を変えないとき、出力は何も変わらなかったことを示す

- Given: ヘッドはドキュメントだけを変更する
- When: 開発者が比較スクリプトを実行する
- Then: 出力は Lint 結果が同じことを示し、ベースとヘッドの時間を警告なしで示す

### ほかの人のプルリクエストの大きな変化に気づく

フォークからのプルリクエストをレビューするメンテナーとして、CI に比較を実行してほしい。プルリクエストをローカルでビルドしてベンチマークしなくて済むようにするためです。

**受け入れ条件：**

シナリオ：プルリクエストがパッケージを変更したとき、CI は比較をジョブサマリーに載せる

- Given: フォークからのプルリクエストが `@textlint/kernel` を変更する
- When: CI がそのプルリクエストに対して実行される
- Then: ジョブサマリーは比較の Markdown の出力を持ち、実行は JSON の出力と CPU プロファイルをアーティファクトとして持つ。CI の成否はほかのチェックだけで決まる

シナリオ：プルリクエストのコードが悪意を持つとき、シークレットも書き込み権限も得られない

- Given: フォークからのプルリクエストが、比較スクリプトを環境を出力してリポジトリに push するように変更する
- When: CI がそのプルリクエストに対して比較を実行する
- Then: ジョブはリポジトリのシークレットを持たず、トークンは読み取りしかできない。push は失敗し、実行の外は何も変わらない

シナリオ：プルリクエストが Lint に影響しないファイルだけを変えたとき、比較は実行されない

- Given: プルリクエストが `docs/` の下の Markdown ファイルだけを変更する
- When: CI がそのプルリクエストに対して実行される
- Then: 比較のワークフローは実行されない

### 遅い部分の CPU プロファイルを見る

遅くなった原因を調べる開発者として、実行の CPU プロファイルがほしい。プロファイラーで開いて、遅くなった関数を見つけられるようにするためです。

**受け入れ条件：**

シナリオ：比較が終わったとき、CPU プロファイルが残る

- Given: 比較を実行した
- When: 開発者が出力ディレクトリか CI のアーティファクトを開く
- Then: 各ビルドの CLI の実行、パーサー、トラバースの CPU プロファイルが、Chrome DevTools で開ける形式である

### AI エージェントから比較を読む

プルリクエストをレビューしたり、遅くなった原因を調べたりする AI エージェントとして、比較を JSON でほしい。表をパースせずに数値を読めるようにするためです。

**受け入れ条件：**

シナリオ：比較が終わったとき、JSON はベース、ヘッド、差を持つ

- Given: 比較を実行した
- When: エージェントが JSON の出力を読む
- Then: JSON は、ベースとヘッドのコミット、文書のセット、片方のビルドにしかない Lint 結果、実行時間、パーサーとトラバースの時間、各ビルドのプロファイル、パッケージごとの CPU 時間を持つ

### 大きな文書のセットで測る

コアの開発者として、約 5、90、1,000、10,000 文書のセットで比較を実行したい。変更がどう規模に効くかを見られるようにするためです。

**受け入れ条件：**

シナリオ：大きなセットを選んだとき、スクリプトは文書を固定のコミットで用意する

- Given: 約 10,000 文書のセットを選び、それがマシンにない
- When: 開発者がそのセットで比較スクリプトを実行する
- Then: スクリプトは、リポジトリの文書をスクリプトが定めるコミットでダウンロードし、次の実行ではダウンロードしたファイルを再びダウンロードせずに使う

なし。この機能に指標は定めていません。

## 機能要件

### 比較スクリプト

**概要：** textlint の 2 つのビルドを作るか使い、同じ文書のセットで両方を実行し、差を書く。

**入力：** ベース（Git の ref。デフォルトは `master`）、ヘッド（デフォルトは作業ツリー）、文書のセット。

**出力：** 標準出力の Markdown と、出力ディレクトリの JSON、Markdown、CPU プロファイル。

#### 適用条件

##### 比べるもの

| 項目 | 出どころ | 理由 |
| --- | --- | --- |
| Lint 結果 | 各ビルドの CLI の JSON の結果 | ホットパスの変更は、意図しない限りルールの報告を変えてはならない。同じ文書は毎回同じ結果を出すので、差はコードの変化である |
| CLI の実行時間 | 各ビルドを数回ずつ、ビルドごとに続けて実行する | 利用者が見る時間。実行ごとに変わるので、大きな比だけに印を付ける |
| 各パーサーの時間 | 組み込みの各パーサーが、セットのすべての文書を 1 つのプロセスで数回パースする | CLI のほかの部分を含まないパースの時間。CLI よりノイズが小さいので、小さい比にも印を付ける |
| トラバースの時間 | カーネルが、すべてのノードの種類を購読して何もしないルールで、すべての文書を 1 つのプロセスで数回 Lint する。パースの時間は含めない | ルールのコストを含まない、木を歩いてリスナーを呼ぶコスト |
| プロファイル | 各ビルドの 1 回の実行の [パフォーマンスプロファイル](../performance-profile/requirements.ja.md) | 実行の時間がどこに使われたかを並べて示す。1 回の実行から得るので、読むためのもので、何が変わったかの判断には使わない |
| パッケージごとの CPU 時間 | 各ビルドの CLI の 1 回の実行の CPU プロファイル | 時間が textlint、ルール、そのほかの依存の間で移ったか |

出力は何が変わったかから始めます。読み手が一目で変化の有無を見て、それから詳細を見られるようにするためです。
ベースに `--profile` がないときは、ベースのプロファイルを欠けているものとして示し、ほかの項目を比べます。

##### 文書のセット

セットは固定したコミットの文書です。ベースとヘッド、別の日の 2 回の実行が、同じ文書を Lint するようにするためです。

| セット | 文書 | ファイル数 |
| --- | --- | --- |
| small | `test/benchmark/examples`（このリポジトリ） | 約 5 |
| medium | 日本語の書籍 js-primer | 約 90 |
| large | MDN の JavaScript のドキュメントの日本語訳 | 約 1,000 |
| huge | MDN の日本語訳 | 約 10,000 |

比較のルールは日本語をチェックするので、すべてのセットは日本語の Markdown です。
ローカルの実行と CI はすべてのセットを使います。開発者は早く終わらせるために一部のセットを選べます。
マシンにないセットは、リポジトリの履歴なしでそのコミットでダウンロードするので、すべてのセットの準備は一度だけ短い時間で済みます。

Lint の設定は `preset-jtf-style` のルールです。正規表現ですべての文をチェックするので、textlint 自身の処理が実行の大きな部分を占めます。

##### しきい値

スクリプトは各ビルドの時間と、ヘッドのベースに対する比を示します。CLI では実行の中央値を、パーサーとトラバースではもっとも速い実行を使います。マシンのノイズは実行を遅くするだけだからです。
CLI では、比が 1.3 以上か 0.77 以下のときに大きな変化として印を付けます。共有のマシンでは、プロセスの実行時間が実行ごとに 10% 以上変わるためです。
パーサーとトラバースは、ウォームアップのあと 1 つのプロセスで実行するので、比が 1.1 以上か 0.91 以下のときに印を付けます。
1 ms 未満の時間には印を付けません。変化とノイズを見分けるには短すぎるためです。

#### 例外時の挙動

##### ビルドが失敗する

スクリプトは止まり、どのビルドが失敗したかを出力する。部分的な比較は書かない。

##### CLI の実行時間を測れない

実行時間を測るツールがマシンにない。スクリプトはほかの項目を比べ、CLI の実行時間は測らなかったと示す。

### CI ジョブ

**概要：** プルリクエストに対して比較スクリプトを実行し、出力をジョブサマリーに載せる。

**入力：** パッケージ、その依存、または比較そのものを変更するプルリクエスト。

**出力：** Markdown の出力を持つジョブサマリーと、JSON の出力と CPU プロファイルを持つアーティファクト。

#### 適用条件

ジョブはプルリクエストのコードを、リポジトリのシークレットなしで、リポジトリの読み取り権限だけで実行します。フォークからのプルリクエストのコードが、シークレットを得たりリポジトリを変えたりできないようにするためです。
ベースはプルリクエストのベースのコミットです。CI は各セットを別のジョブで比べるので、セットは並行して実行され、実行できないセットがあってもほかのセットの結果は隠れません。もう 1 つのジョブが、すべてのセットの結果を 1 つのジョブサマリーにまとめます。
ジョブは差を理由に失敗しません。比較を実行できないときだけ失敗します。

#### 例外時の挙動

##### 比較を実行できない

ジョブはエラーで失敗し、プルリクエストのほかのチェックには影響しない。

### AI エージェント向けの指示

**概要：** AGENTS.md と AI エージェント向けのスキルが、パーサー、カーネル、そのほかのホットパスのコードを変更したときに比較スクリプトを実行し、結果を読み、Markdown の出力をプルリクエストの説明に載せるようエージェントに指示する。

#### 適用条件

指示は、素早い確認と最終確認に使うセット、`--profile` と CPU プロファイルで遅い部分を見つける方法、しきい値の範囲の差を改善と呼ばないことを伝えます。

## データ要件

### 必要なデータ

- **比較の結果：** ベースとヘッドのコミット、セット、異なる Lint 結果、実行時間、パーサーとトラバースの時間、プロファイル、パッケージと関数ごとの CPU 時間。実行ごとに書き、CI ではリポジトリの保持期間の間アーティファクトとして残す。
- **CPU プロファイル：** 各ビルドとセットの、CLI、パーサー、トラバースごとに 1 つ。
- **ダウンロードした文書：** 固定のコミットのセットのファイル。再利用のためにマシンに残す。

### 関係

比較の結果は、セットごとに、ビルドごとの [パフォーマンスプロファイル](../performance-profile/requirements.ja.md) を 2 つ持ちます。

### 個人情報

収集しません。結果は公開リポジトリのファイルパスと、それに対するルールのメッセージを持ちます。

## 外部サービスへの依存

- **GitHub Actions**
  - **関連するユーザーストーリー：** ほかの人のプルリクエストの大きな変化に気づく、AI エージェントから比較を読む
  - **依存する理由：** プルリクエストごとに比較を実行し、JSON の出力と CPU プロファイルをアーティファクトとして残す
  - **契約と利用の判断：** ジョブはリポジトリのほかのチェックと同じホステッドランナーを使う。比較は 4 つのジョブそれぞれで 2 つのビルドを作るので、パッケージを変更するプルリクエストのランナーの時間が増える
- **GitHub**
  - **関連するユーザーストーリー：** 大きな文書のセットで測る
  - **依存する理由：** small 以外のセットは GitHub の公開リポジトリで、固定のコミットでダウンロードする
  - **契約と利用の判断：** 公開リポジトリだけをダウンロードする。その文書は Lint するだけで再配布しない

## セキュリティの考慮事項

フォークからのプルリクエストのコードを CI ジョブが実行するので、ジョブはそのコードが盗んだり変えたりできるものを持ってはなりません。リポジトリのシークレットを持たず、トークンは読み取りだけです。
プルリクエストへのコメントのように、シークレットや書き込み権限を持つジョブは、プルリクエストのコードを実行してはならず、比較の出力を信頼できないデータとして扱わなければなりません。

## 未解決事項

- **しきい値：** 変化に印を付ける比（CLI は 1.3、パーサーとトラバースは 1.1）は、共有のマシンでの実行のノイズから選んだ。暫定の扱い：そのまま使う。再検討の条件：CI が再現しない変化に印を付けたとき、または再現する変化を見逃したとき。azu が決める。
